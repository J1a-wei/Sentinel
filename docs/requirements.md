# Sentinel 产品需求与分期

本文整理已确认的产品目标，以及建议的细化口径与实施顺序。技术栈、部署和升级设计见 [架构规划](architecture.md)，数据模型见 [数据库设计](database.md)；文档描述目标能力，不代表全部已实现；当前资产与采集开发链路及未接入能力见 [实现接口约定](implementation-contract.md)。

## 已确认的目标与边界

| 项目 | 已确认内容 |
| --- | --- |
| 开发语言 | Hub 和 Scout 统一使用 Rust |
| 部署对象 | VM 与裸金属主机，首期优先支持 Ubuntu 22.04、24.04，管理规模为 1,000 台以上 |
| 部署形态 | Hub 与 Scout 支持 systemd 原生服务；Scout 另有特权容器形态。Docker 仅用于容器路线，不再是统一必选前置条件 |
| 原生 Scout 权限与监督 | 原生形态以 root（或经单独评估的等价能力）读取宿主 `/proc`、`/sys`、`/etc` 等；由 systemd 监督单一 Scout 进程 |
| 运行形态识别 | Scout 自动识别 `auto|native|container`；native 根 `/`、container 根 `/host`；显式 `HOST_ROOT` 优先，显式设置但路径不存在时不得回退 |
| Scout 一期能力 | 机器资产与指纹、apt 软件包漏洞、端口、进程数量、SSH 与认证配置、运行状态、面向 AI 的异常诊断能力 |
| 恶意文件检测 | 放到第二期，具体引擎与集成方式待定 |
| 处置边界 | 首期只读检查和告警，不自动删除文件、隔离主机、终止进程或修改系统配置 |
| 后续日志用途 | 优先支持跨主机安全调查，按来源 IP、账号、事件类型等检索与统计 |
| 数据基础设施 | PostgreSQL 保存管理与安全结果数据；NATS JetStream 承担可靠传递；Elasticsearch 保存和检索日志 |
| 主机组织 | 每台主机一个管理分组，支持多个标签筛选 |
| 指标历史 | 分钟级保留 7 天，小时级保留 90 天；采样频率可调整 |
| 界面 | 先确定需求，再据此设计 Hub UI |

原生部署不依赖容器运行时：Hub 与 Scout 由 systemd 作为宿主机服务运行。原生 Scout 直接读取宿主根 `/`，容器形态读取 `/host`；两种形态都必须确认数据来自宿主机而非 Scout 自身运行环境。原生形态的自动升级尚未实现，更新由系统包管理与运维流程负责；容器自动升级仅在容器形态适用。

用户提出的“弱密码问题”和“方便 AI 接管的扫描”仍需明确能力边界。本文建议先以密码策略检查和结构化只读诊断实现，不将密码破解、任意命令执行或自主处置纳入范围。

## 一期功能与建议验收口径

以下细节是将已确认目标落实为可实现需求的建议，具体字段和阈值在实现前确定。

### 1. 机器资产与指纹

- 采集主机名、发行版及版本、运行内核、架构、CPU 型号与核数、内存容量、磁盘、网卡与 IP、启动时间及 Scout 版本。
- 每台主机归属一个管理分组，使用多个标签灵活筛选；标签不用于权限继承。
- 将资产 ID、Scout 安装身份和机器指纹分开：资产 ID 关联历史，安装身份用于实例注册与认证，指纹辅助识别重复登记和机器变化。
- Scout 身份持久化到宿主机，正常重启、容器重建（原生形态为服务重启）及升级不生成新资产；升级实例使用独立实例 ID。
- 不单独使用 IP、主机名或 MAC 作为唯一身份；遇到镜像克隆、重复凭证或指纹冲突时报告冲突，不静默合并两台机器。
- 机器重装后的历史资产绑定方式待定；不能只凭指纹自动继承原主机权限。
- 如使用 `machine-id`，采用应用专用派生值，不直接上报原值。系统镜像克隆还需要正确初始化身份，见 [systemd machine-id 文档](https://www.freedesktop.org/software/systemd/man/latest/machine-id.html)。

验收覆盖身份跨升级保持稳定、IP 变化、克隆冲突、部分字段不可读取，以及信息变更后的历史关联。

### 2. 宿主机软件包漏洞评估

- 采集宿主机 dpkg 数据库中的已安装软件包，不读取 Scout 自身运行环境的软件包清单（容器形态下即容器自身清单）；保留二进制包名、源包名、完整版本、架构和发行版信息。
- 建议 Scout 上报清单，Hub 集中同步官方漏洞数据并匹配；情报更新后可重新评估已有清单，同时展示清单采集时间。
- 匹配需要遵循 Ubuntu 发行版和完整 Debian 软件包版本语义，保留 epoch 与发行版修订号，不能仅比较上游版本字符串。
- Ubuntu 会回移安全补丁，旧上游版本号不等于仍然受影响，见 [Ubuntu 安全更新说明](https://documentation.ubuntu.com/security/security-updates/)。
- 官方 CVE 数据覆盖已知但尚无修复的漏洞，不能仅依赖已发布安全更新；对待确认状态保留其不确定性，见 [Ubuntu OSV 说明](https://documentation.ubuntu.com/security/security-updates/osv/)。
- 对第三方源、自编译或来源不明的软件包，保留来源与覆盖限制；无法匹配不计为安全。
- 结果包含 CVE、软件包、当前版本、适用修复版本、严重程度、判定依据、情报来源和更新时间。
- 结果区分受影响且可修复、受影响但暂无修复、待确认、不受影响或已修复、无法评估。

验收覆盖 Ubuntu 22.04 与 24.04、回移补丁、完整版本比较、第三方包、情报过期和采集失败。磁盘上软件包已更新，不直接证明运行中的内核或服务已使用新代码。

### 3. 端口清单

- 分别采集 TCP 监听端点和 UDP 绑定端点，记录协议、地址、端口、IPv4/IPv6、网络命名空间和采集时间；可获得时关联进程。
- 提供端点总数与明细，明确去重口径；不能将已有连接或所有 UDP 绑定都称为对外服务。
- 支持隐藏回环地址，范围覆盖 `127.0.0.0/8` 和 `::1`；通配监听地址不属于回环地址。
- 建议将 Docker 发布端口及目标映射单独列出，避免与监听端点混为同一计数。Docker 可通过转发规则发布端口，见 [Docker 端口发布说明](https://docs.docker.com/engine/network/port-publishing/)。
- 本地监听、容器发布和外部网络可达性分别表达；第一期不依据监听清单声称已验证公网暴露。

验收覆盖 TCP/UDP、IPv4/IPv6、回环过滤、通配地址、进程退出导致的关联缺失，以及宿主机与业务容器的视图差异。

### 4. 进程概况

- 统计宿主机进程数量，进程与线程分别定义；不能以累计创建进程数或瞬时运行队列长度代替总数。
- 建议补充运行、睡眠和僵尸状态数量；宿主机总数包含其可见的业务容器进程。
- 专项诊断按需采集 CPU、内存占用靠前的进程及必要元数据，默认不上传完整命令行或环境变量。
- 进程关联使用 PID 与启动信息，避免 PID 复用导致历史记录误关联。

验收覆盖进程创建与退出竞争、不可读取进程、命名空间差异和部分采集；采集不全时报告覆盖限制。

### 5. SSH 与密码策略基线

- 检查密码认证、交互式认证、root 登录、空密码、认证组合及用户访问限制等配置。
- 评估应考虑默认值、`Include`、`Match` 条件和运行参数；仅匹配单行配置不足以代表实际策略，见 [OpenSSH 配置说明](https://man.openbsd.org/sshd_config)。
- 区分已解析的磁盘配置与运行中服务的生效情况；无法确认重载或特定匹配上下文时标明限制。
- 密码策略检查关注 PAM 配置、质量要求及例外；交互式认证可能涉及密码或多因素认证，不能一概视为密码登录。
- 规则结果包含适用范围、通过或不通过、执行错误、不适用及无法确认，并提供必要的脱敏证据与修复建议。
- 第一阶段建议不验证现有密码本身的强度，不采集密码或密码散列，不进行登录猜测；界面明确显示“现有密码强度未验证”。

验收覆盖配置包含关系、条件匹配、交互式认证、root 例外和读取权限不足，避免将缺失证据判定为通过。

### 6. 主机运行状态

- CPU：总使用率、核数、负载；明确归一化口径，按需要区分 iowait、steal 等时间。
- 内存：总量、可用量、使用量及 Swap，避免将文件缓存简单视为不可用内存。
- 网络：各网卡接收与发送字节速率，建议附带错误、丢包计数；吞吐速率与链路标称带宽分别表达。
- 建议补充磁盘容量、可用空间、inode 和必要的 I/O 指标，支持识别队列或升级失败的资源原因。
- 速率按相邻采样差值和实际间隔计算；首次采样、计数器重置或重启不能产生虚假峰值。
- 明确物理网卡、网桥、虚拟网卡的分类，避免汇总时重复计数；每条数据记录采集时间和质量状态。

验收确认数据属于宿主机，并覆盖 Scout 自身运行环境（原生进程或容器）的资源限制、网卡变化和采样间隔波动。已确认分钟级保留 7 天、小时级保留 90 天，具体采样频率与资源预算待压测确定。

### 7. 面向 AI 的异常诊断

- 已确认目标是在异常发生时提供便于 AI 参与分析的扫描；实际模型接入时间、模型选型和交互形式尚未确定。
- 建议一期先交付结构化只读诊断任务，支持人工触发，并预留受策略约束的规则触发方式。
- 任务使用明确类型，例如 CPU、内存、端口、软件包或 SSH 专项复查；声明主机、时间范围、允许采集的数据、超时和资源限额。
- 结果包含任务 ID、时间线、证据、相关变化、采集器或规则版本、失败原因和覆盖限制。
- 模型后续可基于证据生成解释或建议限定范围的复查；不通过任意 Shell 执行实现“接管”。
- 默认不采集文件内容、完整命令行或原始日志；扩大采集范围需要明确的策略授权、访问权限和保留期限。

验收关注任务可追踪、超时可终止、范围可约束、失败可解释；诊断结果不足时不能生成确定性的安全结论。

## 建议补充的一期能力

| 能力 | 建议内容 |
| --- | --- |
| Scout 自身健康 | 心跳、最后成功上报时间、版本、启用能力、采集失败、本地队列积压、CPU 与内存占用 |
| 变化记录 | 资产变化、软件包安装/升级/卸载、监听端点变化和 SSH 配置变化 |
| 基础告警闭环 | 持续时间阈值、重复告警合并、恢复状态、维护窗口和故障原因 |
| 采集覆盖展示 | 区分已采集、未支持、未启用、权限不足、过期和执行失败 |

这些补充能力用于区分“未发现问题”和“未完成检查”。具体规则与通知渠道待确定，不扩展为完整监控平台或全套合规认证。

## 后续系统日志能力

日志业务方向与 Elasticsearch 选型已确认；日志收集从哪一期开始、具体日志源及默认启用范围仍待确定。

- 首批日志源可评估 SSH 认证、sudo 和关键服务异常；按主机组配置来源、字段、脱敏规则及采集范围。
- 统一事件时间、接收时间、资产 ID、来源、事件类型、来源 IP、账号、操作结果及必要的脱敏正文。
- 支持按时间、主机组、来源 IP、账号和事件类型组合检索，并进行计数和跨主机统计。
- 典型调查包括同一来源 IP 在多台主机的认证活动、登录失败分布、某账号的登录及 sudo 时间线。
- 日志与管理任务、安全事件使用独立的流和容量约束；明确日志轮转、读取位置恢复、断网补传和重复记录处理。
- 日志查询遵循主机组与角色权限；敏感正文不进入应用运行日志，原始日志的访问和导出另设审计。
- NATS JetStream 的缓冲保留与 Elasticsearch 的查询保留分别配置；原始日志不默认长期写入 PostgreSQL。

验收需测量平均与峰值流量、积压恢复、目标查询耗时及保留成本。字段结构、日志时间可信度、保留期限和删除规则待确定。

## 建议实施分期

| 阶段 | 建议交付 |
| --- | --- |
| 一期 A：资产与运行状态 | 身份与注册、心跳、资产信息、资源指标、进程与端口、Scout 健康、可靠上报及升级基础 |
| 一期 B：安全评估 | 软件包漏洞匹配、SSH 与密码策略基线、定时检查、手动复查和覆盖状态 |
| 一期 C：异常诊断闭环 | 变化记录、基础告警、结构化诊断任务、结果历史与千台以上验证 |
| 二期：恶意文件检测 | 只读恶意文件扫描、规则更新、引擎健康、资源档位与真实覆盖验证 |
| 后续待排期 | 系统日志接入、实际 AI 分析、更多账户及权限基线、进程与网络行为检测 |

一期 A/B/C 是实施顺序建议；恶意文件检测进入第二期已确认。系统日志和模型分析可以独立排期，不预设必须等到第二期完成后才启动。

## 统一验收原则与待定事项

- 所有主机检查都验证数据来自宿主机；原生形态读宿主根 `/`，特权容器读 `/host`，且特权容器不会自动获得正确的全部命名空间视图。
- 结果必须有采集时间、目标范围、判定依据和数据质量；不可用、过期及未知不能显示为零或通过。
- 断网、重连和重复投递需通过稳定任务 ID 和幂等处理避免重复副作用，不得造成资产错误合并；数据丢弃和覆盖空窗应可观测。
- 资源预算覆盖本地队列、诊断任务及升级交接峰值；不得因批量任务无界增长影响宿主业务。
- 应用运行日志不记录凭证、密码、完整命令行或敏感主机原始数据；证据按授权范围与用途采集。
- CPU 架构支持范围、最低主机规格、容器路线的 Docker 兼容版本、采样频率、扫描周期及固定阈值待确定。
- 资产重装与历史绑定策略、身份冲突处置、规则清单、角色权限和日志采集授权方式待确定。
- 后续安全评估 UI、外部通知渠道、日志接入阶段、实际 AI 接入阶段及模型处理的数据范围待确定；一期 A 资产管理 UI 已连接真实 API。

自动处置不在一期验收中。若后续引入，需要另行确定可执行动作、授权、审计、回退和业务影响边界。
